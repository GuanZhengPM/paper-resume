# 岗位内容诊断标准

只使用与目标相关的标准，不按关键词强行给用户换岗位。下列项目是核对和提问方向，缺什么就了解什么，不能将清单自动补写为经历。量化适用时使用真实数据；没有数据时写清可核实的成果。

| role | 重点核对 | 改写与追问方向 |
| --- | --- | --- |
| product | 用户问题、目标、判断与取舍、本人推动的动作、业务结果、复盘 | 把研究、需求与迭代串成因果关系；日常反馈整理只有确实形成分类、发现问题并推动变更时，才能写出这些成果。 |
| ai-product | 产品问题、数据来源与构造、技术方案、评估、业务落地 | 在 product 基础上核对模型或工具的实际使用、版本是否影响方案、Prompt/RAG/微调的选择、验证集口径、线上结果；不能把调接口写成训练模型，把离线提升直接等同业务增长。 |
| operations | 目标人群、增长或运营瓶颈、策略与执行、结果 | 说明行动解决什么问题，以及本人贡献；关注转化、留存、效率或质量的真实口径，不把团队总体增长全部归因给个人。 |
| algorithm | 难题、方法选择、实现与实验、基线、论文贡献 | 说明如何解决非标准问题；展现技术主线、消融或比较证据及本人贡献。Publication 的价值用具体问题和结果说明，SOTA 须有对应基准与条件。 |
| ai-infra | 系统位置、上下游、工程动作、性能或可靠性结果、权衡 | 简短概括贡献，再说明场景、结果、技术动作与影响；核对成本、吞吐、延迟、稳定性等测试条件和生产范围。 |
| embedded | 硬件环境、技术栈、调试或设计动作、约束与交付结果 | 从“用了接口”进一步问解决了什么问题；核对时延、成功率等指标的测试条件，保留系统约束。 |
| robotics | 规划或控制所处层级、算法与仿真工具、选择依据、实测挑战 | 核对任务、行为、轨迹规划与控制的实际工作边界，以及噪声、仿真到实机等问题；不要默认用户做过所有层。 |
| backend | 系统问题、技术选型、优化动作、性能结果、本人负责范围 | 指标保留前后值与负载条件；技能熟练度按用户可说明、可验证的程度写，不自动升级“了解”为“精通”。 |
| general | 专业职责、目标相关性、可核实成果、职业脉络 | 用本行业准确且易懂的语言消除模糊表达；HR、财务、行政等也可描述效率、质量和覆盖范围，不强制每段出现百分比。 |

plain 模式对所有岗位通用：只改善表达，不强制上述内容全部具备，不添加评价性口号。必要的加粗用于突出已核实的核心动作或成果，避免整段加粗。
